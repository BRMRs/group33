# Participant directories and pairing-code deletion — local candidate

Refs #10 / #16. Main `64ddd4e26440d60a60f209dd7eb12d102e2a55dd` and Issue/PR scope were verified on 2026-10-27. Thirty-three source/test/build dependencies come from the previous lifecycle HTTP candidate; thirty remain unchanged. This candidate changes the memory Store, PostgreSQL Store and HTTP configuration, and adds a directory service/controller, additive v4 SQL and three test suites. This is local preparation, not a published commit, PR or production deployment.

## Behavior and contract mapping

GET /api/v1/pairing-requests returns the existing ItemsResponse<PairingRequestView> for the authenticated participant. Optional status accepts exactly one existing PairingRequestStatus; omit it to include all retained own terminal states. Expiration is resolved at the transaction time before status filtering, so a request at its deadline is absent from PENDING and present as EXPIRED/CODE_EXPIRED. Expiry mutation and SQL reads are scoped to the participant/role, never an arbitrary body/query actor. Unknown/duplicate/blank filters and unsupported actor/Elder filters return 400 MALFORMED_REQUEST.

GET /api/v1/care-relationships returns existing ItemsResponse<CareRelationshipView> for that participant, including ACTIVE and REVOKED. An unrelated authenticated caller receives an empty collection, without knowledge of other users' histories. Rows use stable ID order as an implementation choice, not chronological or business ordering. There is no invented paging/truncation field or automatic terminal deletion. No medical fields or authorization are added by list membership.

DELETE /api/v1/pairing-codes/{id} requires the current trusted Elder actor, a full single UUID operation header and absent body or empty JSON. Removing the current code, closing any associated PENDING request and storing the successful deletion receipt share one transaction. An unexpired PENDING request closes CANCELLED/ELDER_CANCELLED; at/after its original deadline it remains EXPIRED/CODE_EXPIRED. ACCEPTED requests and existing ACTIVE relationships are preserved. Caregiver calls return ROLE_NOT_ALLOWED; another Elder's existing code and a missing code have the same generic RESOURCE_NOT_ACCESSIBLE result.

Deletion receipts are private to actor/UUID in the dedicated deletion namespace and bind installation, code ID and the existing canonical fingerprint. The private matching receipt retains ownership evidence after the active-code row has been removed. Exact successful retry returns empty 204, including after a replacement is issued; it cannot remove the replacement. A changed target that is currently owned returns IDEMPOTENCY_KEY_REUSED; an unrelated target remains generic unavailable before binding diagnostics. A new key for a no-longer-current code returns generic 404; idempotency here is the accepted original command/key, not an invented public code-history endpoint. Replaying the old issuance receipt does not restore the deleted opportunity.

## Transactions, persistence and errors

PairingDirectoryStore is an extension of the previous decision Store. The memory adapter extends the same bounded global lock/copy-on-write state, not a separate code repository. The PostgreSQL adapter uses the same database guard transaction for lists, code removal, pending closure and deletion receipt. SQL participant predicates derive from the trusted enum/ID, with no user-selected SQL column. The earlier request row mapper is reused for detail and collection reads. Success receipt UPSERTs reject installation/fingerprint/target replacement; active-code deletion has no cascading removal of retained request or operation evidence.

The v4 prototype adds only pairing_code_deletion with actor/UUID primary key. It deliberately has no FK to the removed active-code row. v1/v2/v3 are unchanged; upgrade and repeated v4 application preserve populated request data. Older service operations continue using the v3 tables; new directory/deletion operations require v4. This is not a production migration-framework selection, role/grant setup or automatic Boot database wiring.

HTTP uses the existing signed-JWT/current-user resolver and Shared DTOs. Cache-Control is no-store; structured errors retain matching X-Request-ID. Lock contention is 409 OPERATION_IN_PROGRESS, retryable=true and Retry-After: 1. JDBC/service failures are private-detail-free retryable 503, including real deferred COMMIT failure. Original keys remain usable after rollback. Existing strict JSON/header/media/query checks apply to code deletion. The default HTTP Store remains in memory; real PG is selected only by test configuration.

## Remaining boundaries

Anonymous user/session identity is still memory-backed, and phone/account identity remains a separate recorded decision. Persistent pairing records alone do not recover identities after server restart. Production DataSource/pooling/TLS, formal migrations, private grants, environment selection, deployment and device integration remain pending.

CareRelationshipAccess stays the original deny-all bean. Lists and receipts do not authorize medical/photo/plan reads or writes. Future protected business transactions must check current relation and serialize with revocation. Those adapters must not turn the list into an authorization cache. #10/#16 stay open.

Formal PR dependency sequence, scope and named non-author Server/security/persistence plus Android review remain to be recorded; the #47 issuance-only backup is not automatically extended. This cohesive Store/HTTP/schema/test change exceeds the normal 500-line guideline because the invalidation/list boundary requires real race, rollback and restart evidence. No existing PR, formal approval or main branch is modified.
