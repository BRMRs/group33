## Behavior

- Use the configured HTTPS project origin and existing private bucket. Origin/key/bucket are trusted deployment inputs, never caller-selected HTTP fields. Reject userinfo/query/fragment/path origins, unsafe bucket segments, non-server key types, invalid budgets and redirect-following clients. Default TLS certificate verification remains active; test custom trust is confined to fixture construction.
- Support modern server `sb_secret_` credentials through `apikey` only; no group33 JWT, signed/public download URL, source filename or raw provider diagnostic is returned. Do not register the privileged adapter directly for public access. The existing business service must check current identity/relationship before calling read, and retain its STAGING/READY/receipt transaction boundary separately.
- GET bucket metadata before each operation; require matching id and a Boolean public=false. This rejects a bucket that becomes public before the next call, but cannot prevent an external administrator changing its policy during a request. RLS/grants/private-bucket setup and server logging sanitization require real deployment verification. No automatic bucket create/update/delete or policy changes.
- Object name is the original UUID plus `.blob`; no caller paths. Upload opaque already-validated bytes as application/octet-stream with x-upsert=false. Configure the dedicated private bucket to allow that content type (or no MIME restriction) and at least the existing five-MiB bound; image validation and outward content type remain the unchanged business layer's responsibility.
- Before upload, authenticated GET either verifies the exact byte count/SHA256 and returns the original key without consuming the retry source, or recognizes documented NoSuchKey and validates the entire bounded source before POST. Existing different content is OBJECT_CONFLICT; no PUT/upsert/delete/overwrite path exists. Caller owns the source stream, including on error.
- A successful upload status or ETag alone is insufficient: read the exact stored object and verify count/SHA256 before returning success. Concurrent POST conflicts and the explicit legacy Duplicate response are reconciled by verified bytes. Acknowledgment without an object or unresolved conflict stays UNAVAILABLE. An unknown/transient write may have committed; explicit retry uses the same object/key and recovers by readback. No new identity or hidden automatic retry.
- Only documented 404 NoSuchKey maps to MISSING. Missing bucket/tenant, unknown 404, denial, rate limit, provider failure, malformed metadata/error and transport/TLS failure stay safely UNAVAILABLE. Raw causes, provider messages, endpoints, keys and bytes never escape PhotoObjectException; adapter toString is redacted.
- A combined maximum120-second monotonic HTTP budget covers bucket/object lookup, upload and full verification body, with default10-second connect timeout. Bounded reactive subscribers cap success bytes to expected length+1 and JSON/errors to16KiB; body stalls after headers are cancellable. Interrupts preserve the caller flag. Caller stream reads are byte-bounded and checked between reads; an arbitrary caller-owned blocking InputStream is not forcibly closed/interrupted. Current business callers supply already captured/validated bytes; an eventual HTTP adapter still owns the complete inbound request budget.
