# Pairing request PostgreSQL adapter — local preparation

Refs #16 / #10. Last verified main `64ddd4e26440d60a60f209dd7eb12d102e2a55dd`, plus the recorded local PostgreSQL issuance and in-memory request service candidates. Remote refresh failed twice with connection/EOF errors during this run; this is not a new claim about current remote state. No real branch, PR or published contract is modified. The dependency bundle intentionally contains the old JDBC adapter beside the new request Store interface; this patch resolves that incompatibility. It is a comparison bundle, not a buildable reviewed commit or an approved stacked PR.

PostgresPairingCodeStore now implements PairingRequestStore. The same real PostgreSQL guard row and transaction serialize issuance, consumption, replacement, requests, receipts and installation/address attempts across connections. Request code_id is unique. Consumption checks the active code's identity/hash/deadline; retained request rows prevent later reconsumption even after replacement/expiry. New requests do not grant relationships. Replacement cascades CANCELLED/CODE_REPLACED or EXPIRED/CODE_EXPIRED using the same supplied transaction time. Current status and original receipt are read separately; stable request identity/participant/display/expiry columns reconstruct the original PENDING success while detail resolves current terminal status.

Request operation primary keys scope actor/UUID; binding and accepted receipt cannot be replaced through the adapter. A receipt references the retained request through an FK; participant ownership and exact initial view are checked before insertion. Private normalized request fingerprint is retained, no new raw-code column is introduced. Existing encrypted issuance receipts/AES-GCM code material are reused unchanged. Display names are stored as private database metadata, not encrypted by the code-receipt cipher; normal identity authorization and production database grants remain required. No credentials or raw code are logged.

pairing-request-store-v2.sql adds three prototype tables after the unchanged v1 schema. It adds request status/reason checks, consumption uniqueness, receipt FK and scoped ordinal rate records; no destructive upgrade or automatic cleanup. This is not a selected production migration tool/history. Current status constraints cover only the implemented PENDING/expiry/replacement slice; future accept/reject/cancel/revoke need a reviewed forward schema extension. The guard is intentionally coarse and is not a throughput or distributed-failover benchmark.

22 new real PostgreSQL tests passed, plus all 22 prior issuance database tests. Only the old suite's schema setup was changed to install v2; original assertions remain intact. New coverage includes reconstruction, exact strings/expiry, deadline-1/exact/+1, unique/FK/check constraints, participant isolation, accepted receipt and rejection binding, eight same-operation connections, eight distinct consumers, eight-installation-limit and 24-IP-limit races, actual SQL and deferred COMMIT errors, replacement COMMIT rollback, real lock wait crossing expiry, NOWAIT recovery, renewal/consumption race, repeatable additive schema installation, callback rollback, separate submitting/replaying JVMs and actual PostgreSQL stop/start. Every integration test executes against local PostgreSQL 17.11; no H2 or in-memory fake stands in for JDBC. Test-only triggers/child entry points are excluded from production packaging.
