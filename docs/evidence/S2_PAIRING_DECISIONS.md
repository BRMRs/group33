## Outcome and boundaries

The trusted-actor application service implements accept/reject/cancel/revoke using existing Shared views. Only the target Elder may accept or reject. Code entry stays PENDING and grants no access. Acceptance records both display identities, changes the request to ACCEPTED with its relationship ID, creates one ACTIVE relationship and saves the success receipt atomically. The Store enforces one ACTIVE Caregiver per Elder; one Caregiver may serve several Elders. No Shared fields, public routes, authentication settings, or SQL are changed.

Either participant may cancel a pending request, retaining the correct participant reason. Rejection/cancellation never reopen the consumed code. Expiry is exclusive and checked after transaction entry; terminal state is not rewritten by a late command. A new accept/reject/cancel command on a closed request fails with PAIRING_REQUEST_CLOSED. A newly issued code still closes pending opportunities without revoking an existing relationship.

Either participant may revoke the relationship. Revocation preserves history and the first revoked time; a later explicit revoke returns that same revoked view without another effect. Participants retain access to their own terminal request/relationship metadata, while unrelated callers receive the same RESOURCE_NOT_ACCESSIBLE result for absent and existing targets. A known Caregiver cannot accept/reject (ROLE_NOT_ALLOWED). All caller identities are trusted authentication outputs, never request-body subjects.

Operations are scoped by actor, action and UUID, with installation and canonical target/empty-payload fingerprint binding. Current participant/role access is checked before replay or target mismatch errors. Success receipts are immutable, distinct from current resource state, and committed in the same transaction as the effect. Rejected operations retain binding and may be explicitly retried with identical input after a precondition changes. The original accepted relationship receipt can still say ACTIVE after revocation; replay does not mutate state or restore access. The original request receipt remains PENDING with no relationshipId even after acceptance. No auto-resume policy is added.

## Store, authorization and persistence limitations

PairingDecisionStore extends the request Store with a separate capability. InMemoryPairingCodeStore shares the original bounded lock and copy-on-write transaction across issuance, consumption, decisions and relationships. Exceptions roll back relationship, request and receipt together. Lock contention returns OPERATION_IN_PROGRESS with one-second retry metadata. No automatic expiry-based deletion removes P0 receipt evidence.

StoredCareRelationshipAccess performs a fresh active-relationship lookup. It is explicitly **not a Spring bean**; the shipped deny-all adapter remains unchanged. A failed or busy lookup never returns permission. This lookup alone is not an atomic authorization-and-medical-write transaction: protected business writes must join their future persistence transaction and serialize with revocation. No production API is now authorized by this candidate, and no device can yet perform this flow through HTTP.

The existing local PostgreSQL request adapter still implements PairingRequestStore and remains unchanged. Its v2 prototype schema supports only PENDING/CANCELLED/EXPIRED, not this relationship lifecycle. A future forward schema and adapter extension must persist relationships, unique active-Elder constraints, request transitions and decision receipts together, with real concurrency/restart tests. This candidate claims only process-local behavior; restart loses data. It does not establish production 30-day metadata retention or durable P0 deduplication. Identity/session wiring, phone-login decision alignment, HTTP status/header mapping, lists, deleting an unused code, SQL migration choice, UI and two-device acceptance remain open.
