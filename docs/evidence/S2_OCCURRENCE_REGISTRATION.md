## Behavior and invariants

- Only a trusted Elder actor for the same target may register. Installation belongs to that actor; batch operation binding includes actor, installation, target, canonicalization version and complete typed request/item order. Foreign/missing plans return the same inaccessible result before field details; accepted operation replay precedes revision/time validation.
- Accept a batch of client-generated evidence, never generate independent preview occurrences. Canonical identity is exactly `(planId, localDate, localTime)`; revision and offset are excluded. Generation UUID is separately unique per Elder. No evidence eviction or implicit device migration.
- Validate owning plan, retained confirmed active revision, real ISO nominal date/time, inclusive retained date range, configured time, exact execution zone and P0_TIME_V1 frozen instant/offset. Use the same existing gap/fold resolver as plan overlap validation. Four golden vectors cover New York gap/fold, Lord Howe half-hour gap and Apia skipped day. Source snapshot nonblank/timestamp checks do not certify snapshot authenticity or exact Room generation-window behavior.
- Preserve retained Medication text, revision and instant/deadline through later edit/deactivation. Old retained revision alone is not rejection. Registration can arrive after changes. For an already accepted exact generation in a new batch, replay the original receipt without re-resolving its frozen time under a later resolver/TZDB. Contradictory evidence receives scoped private validation rejection; no historical overwrite or silent conflict winner is provided. Client Needs attention presentation is future integration, not implemented here.
- Validate the complete batch before business writes. Duplicate generation/tuple, empty items, invalid final item or contradictory existing evidence rejects the batch without partial events. Rejected bindings are retained separately and cannot be rebound; explicit same-intent retry after a missing confirmed revision appears can succeed. Accepted receipts preserve original IDs/times/status and item order across retries/process/database restarts.
- Capture initial SCHEDULED/DUE/MISSED according to service receipt time and the unchanged two-hour `[plannedAt, plannedAt+7,200,000)` interval. This registration-only snapshot is not the later action/reconciliation/lifecycle service: timely offline Taken correction, independent thirty-minute notification, group Help/snooze and follow-up are not delivered.
- Memory copy-on-write and JDBC use the existing single shared plan/pairing guard, so current ownership, retained revisions, event insert and operation receipt commit together with plan edits. Independent database connections/processes share bounded row contention; private service results distinguish in-progress from safe transient failure. No HTTP status/header behavior is claimed by these private result enums.

## Persistence

Explicit additive local prototype `occurrence-registration-store-v9.sql` follows v1-v8. No startup DDL/runtime flag/configuration changes. Uniqueness excludes revision/offset; FK retains the actual confirmed revision/owner/Medication. Deferred batch checks require complete matching operation/receipt/event evidence at COMMIT. Orphan events, omitted response items, mismatched frozen text/zone and mutation/deletion of accepted evidence fail. The JDBC adapter reuses the same connection and database guard as existing plan operations.

The registration-only row and receipt are immutable in this prototype. A future Dose action implementation needs a reviewed forward schema/transaction boundary for changing presentation/status while retaining generation evidence; no permissive update seam or fabricated group API is added now. The SQL prototype is not a reviewed production migration system or cloud installation.
