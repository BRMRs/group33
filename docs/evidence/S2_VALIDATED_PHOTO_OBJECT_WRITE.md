# Validated private photo object write — local integration

Refs #13 / #20. Baseline main `64ddd4e26440d60a60f209dd7eb12d102e2a55dd` plus six byte-identical source/test files from the existing local PhotoInputValidator and LocalFilePhotoObjectStore candidates. Those dependencies are not merged code, new work in this slice, or a formally authorized stacked PR. Their source identities and combined/dependency patches are preserved in the delivery packet.

The internal ValidatedPhotoObjectWriter first validates the actual file and MIME, then builds the object key from the validator-owned byte count and SHA256 and stores precisely those copied bytes with putIfAbsent. Rejected input never calls storage. The application service must supply a trusted, stable, server-allocated UUID and perform authorization before calling; no object ID is generated per retry. Supported MIME casing is normalized to the actual image type. A Stored result means only that object bytes are available, not photo READY, a receipt, permission, or committed metadata. Rejected and StorageFailed are private result types, not new HTTP codes.

Thirteen new test executions use actual generated PNG/JPEG and the real private POSIX filesystem adapter. They cover exact bytes and hash, fresh-adapter reads, permissions, unsupported MIME/mismatch/corrupt/truncated/oversized inputs with zero writes, same-key replay, conflicting bytes, invalid retry against an existing object, original caller-array mutation, unavailable root/retry, and eight independent concurrent adapters with two payloads (four matching successes and four conflicts, one immutable object).

A test-only wrapper throws UNAVAILABLE after the real store successfully publishes to exercise uncertain-response retry; another changes the original caller byte array at the store boundary. These wrappers supplement real file operations, not network/process-crash proof. Existing unchanged storage tests separately exercise subprocess restart/abrupt partial-write halt. These local observations do not establish power-loss durability or Linux/Supabase behavior.

This bounded seam has no Spring/HTTP registration, multipart transport, authentication, photo metadata, business receipt, PostgreSQL transaction, READY publication, lease/reconciliation/cleanup or signed URLs. StorageFailed does not mean nothing was written: the caller must retain the same object identity and payload for safe recovery, and must not delete an uncertain object without reference/lease checks. Local POSIX and trusted service-account assumptions from the storage candidate still apply. No cross-device upload or cloud acceptance is claimed.
