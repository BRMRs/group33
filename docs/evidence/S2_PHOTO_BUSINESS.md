# S2 local photo business candidate — 2026-10-27

Refs #13, #16, #20. This is a local integration candidate based on main `64ddd4e26440d60a60f209dd7eb12d102e2a55dd`, not a published PR or a production acceptance record. It layers the separately saved local persistent identity/pairing runtime and private POSIX object adapter. Those unmerged dependencies are not new contribution credit here.

The opt-in `PHOTO_ENABLED=true` configuration enables exactly the three photo routes in API_CONTRACT. Elder self-upload creates a stable operation/photo/object reservation before filesystem IO. After object integrity and availability are confirmed, READY metadata and the original four-field MedicationPhotoView receipt commit together. PostgreSQL and object storage remain separate systems; uncertain or failed publication retains a private STAGING recovery reservation. There is no cleanup job, expiring upload reservation or public object URL.

Content and list requests use verified persisted anonymous identity. Current ACTIVE Caregiver authorization is read under the same pairing guard as revocation; content IO holds that guard. Revocation prevents subsequent reads; bytes already delivered to an authorized client cannot be recalled. Elder self-access survives relationship revocation. Other medical endpoints retain their existing deny-all relationship adapter.

The business limit remains 5,242,880 bytes and 20,000,000 decoded pixels, JPEG/PNG only. Actual bytes, hash and canonical media type bind the operation. Multipart filename, boundary and MIME parameters do not change an intent. File validation returns 413/415/422, with `file`-scoped INVALID_IMAGE or TOO_MANY_PIXELS for 422. Corrections to fully submitted rejected input require a new key; original payload retries keep the old key. READY and accepted receipts cannot be overwritten.

Transport parser limits are intentionally distinct: at most 6 MiB per file and 7 MiB for the full envelope. Complete near-boundary files reach the business validator and persist rejection fingerprints. A request exceeding these transport safety limits returns 413 before the complete payload is available; it has no application-level payload fingerprint or accepted receipt. This boundary requires cross-side review; it must not be described as a persisted business rejection for every possible 413. Malformed multipart is 400. Controller-independent advice handles parser failures that occur before handler selection. A real 5 MiB+1 request previously returned 500; the original failing evidence is preserved in the local packet and the strict 413 assertion is retained.

New tests: MedicationPhotoServiceTest 16; MedicationPhotoHttpTest 12; PostgresMedicationPhotoTest 12. The latter uses actual PostgreSQL, real private object files, independent connections, SQL and deferred COMMIT fault injection, current relationship/revocation, concurrent identical operations, constraints, store reconstruction and a real database restart. Packaged real-TCP tests additionally exercise a valid exact-boundary PNG, envelope overflow, failure after object write, full application process restarts, stable photo ID/receipt, old JWT identity resolution and revoked access. Test-only fixture code is absent from the production jar.

Reproduction and final counts/hashes are in the external `S2-photo-business-local` evidence packet. Run its prepare_snapshot.py, run_checks.py full/postgres and photo_tcp_smoke.py; credentials remain in existing owner-only local files, never source/log/result JSON. gate1Check/test, policy, lint, APK, bootJar, manifest and patch application are required evidence. Cached or UP-TO-DATE module reports are not represented as fresh execution.

Schema v6 is an additive manually applied prototype under db/prototypes, after v1-v5 in a disposable schema. No production migration framework is selected; startup only verifies required columns and never executes DDL. Rollback is disabling PHOTO_ENABLED; do not drop accepted metadata, receipts or private objects. A future deployed migration/backup/restore plan requires review. Use a separate empty local demo schema and 0700 object root for practice.

Still pending: named non-author Server/privacy/persistence review for this broader slice, E/C2/Android integration, real Supabase adapter and credentials, deployable migration/pool/lifecycle policy, target-device upload memory/timeout budgets, full cloud/local fallback demonstration, Medication/plan transaction and snapshot/history integration. Existing HTTP paths and Shared DTOs remain unchanged. Server error codes are mapped to Chinese/English resources by Android; this slice adds no UI strings or pages.
