# S2 versioned-schema startup validation

Refs #16. Parent Draft #90. Exact source tree, reports and packaged execution records are kept in the external S2-schema-startup-gate-20261030 evidence packet.

Adds a default-off postgres-local startup guard: compare release manifest against the same runtime database/schema in a bounded read-only transaction, reject missing/manual/partial/changed/future/failed/reordered history, preserve existing business-table and encrypted-receipt checks, no automatic migration or administrative credential. Ordinary manifest tests compare with the pinned Flyway checksum implementation. Flyway remains absent from the application jar. See [operator scope and rollout](../SCHEMA_STARTUP_GATE.md).

Fifteen new actual PostgreSQL cases passed: matching fresh Flyway history, database-enforced read-only verification with unchanged history, empty/manual schemas, explicit V5-to-V9 upgrade, eight history corruption variants, qualified schema isolation, valid history with broken business column, and actual Spring runtime Bean creation fail/recover. Manual schema opt-out remains compatible; all disposable schemas are removed. Twelve new standard cases cover release provenance, ten malformed manifests and memory-fallback refusal. Final full-suite results: Server627 + Shared18 + Android51/51 = 747 standard report instances; 261 actual PostgreSQL cases (246 inherited +15 new), all zero failures/errors/skips. Full gate104tasks:46 executed/47 cache/11 up-to-date; Server and both Android test variants executed; Shared tests came from cache. Actual migration ZIP and application bootJar passed 112 packaged checks /39 business requests, including enabled-gate refusal of altered/missing/future history and memory fallback, followed by existing pairing consent/private photo/plan/registration/fault/concurrency/revocation flow and real whole database/Server restart. No private migration account is passed to the application. Disposable schemas/files are removed and the dedicated database stopped. These results are not substitutes for future cloud or device acceptance.

No SQL migration, Shared DTO or wire protocol is altered. No actual Supabase/Render setting/data/resource is changed. The separately maintained Supabase adapter is not silently overwritten; its startup-gate integration, manual cloud schema adoption, phone/V2 work and real device acceptance remain open. Formal human review, operator rollout and main integration remain required.
