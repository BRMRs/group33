# PostgreSQL local runtime and anonymous identity persistence

Refs #16 / #10. Verified main `64ddd4e26440d60a60f209dd7eb12d102e2a55dd` and the current identity/persistence task discussion on 2026-10-27. This local candidate builds on the directory/HTTP/PG sources. It does not select a phone/password identity provider or change the accepted anonymous-login request/response. Formal scope, dependency landing order and non-author Server/security/persistence and Android review remain to be recorded; this packet is not a PR, CI run or production release.

## Runtime and identity

A new AnonymousIdentityStore seam preserves the existing AnonymousUserStore facade consumed by AuthService and the verified JWT actor resolver. Default memory mode preserves the existing installation mapping, name update and fixed-role behavior. In postgres-local mode, the identity repository and all pairing services use the same configured PGSimpleDataSource/schema. PostgreSQL's unique installation constraint and role-conditioned UPSERT atomically recover one stable user ID, update its display name and reject a role change. ID lookup never creates an identity from JWT claims. SQL/COMMIT failures are converted to a private-detail-free IdentityStoreUnavailable; a specific advice returns retryable 503/no-store for login and authenticated actor lookup, rather than claiming an invalid identity or exposing database errors.

v5 adds only anonymous_identity, with unique installation, fixed role and existing field-length constraints. It is additive prototype SQL, not a phone account schema or automatic migration. Existing in-memory identities are not automatically migrated; operators must use a clearly separate fictional local demo or a separately reviewed identity migration. Persistence of the existing installation ID does not promise recovery after that client ID is lost, reinstallation or device replacement.

Explicit app.persistence.mode accepts memory or postgres-local. Typos do not silently select memory. The PG mode requires a loopback JDBC URL with an explicit database and no embedded userinfo/query; a bounded safe schema identifier; separate login/password properties; stable non-placeholder JWT signing material; and an owner-only regular file with exactly 32 binary receipt-key bytes. It verifies required initialized table/column presence and the guard row, then authenticates existing issuance receipt ciphertexts with the configured key. A wrong historical receipt key fails startup before serving. Startup never runs DDL or silently falls back to memory.

The existing PostgreSQL 42.7.14 dependency is promoted to implementation for actual DataSource construction, with its version moved into the existing central catalog (no version upgrade). This is an explicitly unpooled local DataSource with bounded connection/socket waits. Remote/cloud URLs are rejected. Production pooling/TLS/certificates, least-privilege grants, runtime schema version enforcement and cloud selection remain future work; postgres-local is not a Render/Supabase production profile. Stable JWT and receipt keys must be retained privately across restarts; no rotation protocol is introduced.

## Provisioning and configuration

.env.example contains names and safe descriptions only. The application YAML maps explicit PERSISTENCE_* variables plus the existing JWT_SECRET. The packet's runtime_local.py convenience launcher prepares only group33_pairing_local_demo in the already-owned private practice database, applies the five trusted prototype scripts explicitly in one transaction, creates a separate owner-only stable signing file without overwriting an existing file, and starts the packaged application bound to loopback. Credentials are loaded privately, never put in command arguments or result output. The helper is local workspace tooling, not a replacement for a team migration/deployment system.

No formal migration tool is chosen here. The engineering requirement to record that choice and create an ordered migration directory applies before a production schema PR. These prototype scripts remain explicit preparation only. Startup table/column checks are not a complete migration-history/checksum or constraint audit. No destructive downgrade is supplied; existing prototype records remain intact. The local demonstration schema is retained empty for the user's next start; disposable test schemas are removed.

10 new configuration cases cover memory default, mode typo, remote/userinfo/query URLs, unsafe schema/default JWT, invalid/public/missing key files and missing credentials. They preserve private-detail-free exceptions and reject invalid settings before connecting. Eight new real PostgreSQL identity cases cover stable reconstruction, exact name update, fixed role, eight concurrent same-installation and conflicting-role callers, deferred insert/update COMMIT rollback, SQL uniqueness/role checks, missing-table safe failure and real database restart. Prior pairing tests remain unchanged.

Standard reports total 289 (Server191, Shared18, Android40+40), all passing with executed/cache modes recorded. Database tests have 93 actual executions (previous85 plus new8), zero failures/errors/skips. gate1Check/test, lint/APK/bootJar, source policy, hashes and layered patch checks are recorded in the packet. These are local results, not GitHub CI.

A separate packaged-jar PostgreSQL TCP test performs 33 checks. It registers two fictional installations, issues/consumes a code and accepts a relationship; fully stops the application process, starts a fresh process, verifies the old JWT against persisted identity, restores the same IDs through normal login, rejects role change and replays the original encrypted code/acceptance results. It then revokes, stops and starts the entire server again, and confirms REVOKED/current-state retention despite replaying the historical ACTIVE receipt. Renaming the identity table produces safe retryable HTTP503 for login and authenticated lookup; restoring it recovers service. Separate real process starts refuse missing schema, default signing secret and the wrong historical receipt key. All own application processes stop and the disposable schema is removed.

The first TCP probe incorrectly included psql's SET command tag when comparing a scalar row count. Its exact 2|1 identity/relationship assertion was retained; the helper now selects the result line. The failed partial result/log and repair note are preserved, while the final report explicitly records completed=true. An additional actual convenience-launcher start/health/stop check confirms the user's saved startup path works. No token, pairing code or identity values are written to result files.

## Remaining scope

This does not implement phone/password authentication, cross-device account recovery, clinical/photo/plan persistence, production clinical authorization, Render/Supabase access or full two-device acceptance. CareRelationshipAccess remains the original deny-all bean. Pairing rows and persisted identity do not by themselves enable medication services; protected reads/writes must be integrated with current authorization and revocation in their actual business transactions. No existing PR, approval or branch is changed; #10/#16 stay open.

The runtime, identity storage and failure tests stay together so review can verify the live HTTP identity contract across process death and rejected configuration. The original issuance-only reviewer backup is not automatically extended to these identity/runtime boundaries. Formal review and integration remain required.
