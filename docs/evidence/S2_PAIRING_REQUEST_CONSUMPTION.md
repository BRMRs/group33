# Pairing request consumption — local candidate

Refs #10; main `64ddd4e26440d60a60f209dd7eb12d102e2a55dd` plus the three source/test files from PR #47 at `3dcb4a8a8824826b64cd6f97d0fa71eed4e851f9`. This local candidate modifies two of those dependency files and retains the original 17-test issuance suite byte for byte. It is not a change pushed to #47 or an approved stacked PR. The local dependency, own and complete patches are preserved separately.

The plain PairingRequestService accepts a trusted Caregiver, UUID operation, existing RequestPairingRequest and transport-resolved InetAddress. It produces one existing PairingRequestView in PENDING, retaining the code's original exclusive deadline and authenticated display identity. No ACTIVE relationship is created. Current role and operation installation/payload binding are checked before accepted receipt replay; rejected attempts retain their binding and may only be explicitly retried with the same payload. Accepted receipts are distinct from current resource state and remain the original PENDING result even after expiry or replacement; participant detail returns current terminal state. No raw code is stored in request records or logged by the service; diagnostics are redacted.

The existing InMemoryPairingCodeStore is extended, rather than introducing a second disconnected code store. Code, request, consumption marker, operation receipt/rejection and both rate buckets share one bounded lock/copy-on-write transaction. First consumption wins; a code stays reserved for collision detection until replaced/expired. Replacement receives its transaction's current time and atomically closes the old pending request with CODE_REPLACED; a request already at its deadline remains EXPIRED/CODE_EXPIRED. Failure writing either the issuance or consumption receipt rolls all associated changes back. No terminal state reopens a consumed code.

Limits use the accepted defaults 5 attempts/minute/installation and 20/minute/IP. Invalid, expired and consumed codes count; accepted receipt replay does not perform another guess or debit. Rejected attempts within capacity consume both buckets; rate-blocked requests do not prolong the window. When both buckets block, Retry-After seconds cover the longer remaining interval, rounded up. Time is read after the transaction is obtained. The service accepts a typed address to avoid textual IP aliases and does no DNS. HTTP must resolve peer/trusted-proxy provenance; untrusted forwarded headers must not be used. Wrong-role and binding-conflict requests perform no code lookup.

32 new JUnit executions cover leading zeros, role/binding, deadline-1/exact/+1, original receipt vs terminal detail, participant isolation, 30-day in-process terminal retention, replacement and replay, generator collision reservation, both rate limits and their different recovery times, same-key/different-actor concurrency, eight simultaneous code consumers, concurrent replacement/consumption, transaction wait crossing expiry, contention and two real rollback paths with test-only fault injection. Original 17 issuance tests remain unchanged. No test waits real minutes; the clock is controlled.

Internal PairingCodeTransaction.replaceActiveCode now takes the transaction time so cascade/expiry share one instant. This is an intentional local seam change: the earlier local PostgreSQL adapter must be updated and its integration tests rerun before combining it. This packet does not claim compatibility with that adapter, persistence, restart retention, HTTP/JWT/proxy headers, active relationship limits/authorization, accept/reject/cancel/revoke commands, UI, or two-device behavior. Retention is process-local only; there is no 30-day eviction or durable P0 receipt guarantee. Production schema, bounded request/input capacity and privacy retention still require persistence/security review.
