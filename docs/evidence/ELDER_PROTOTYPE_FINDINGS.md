# 长者提醒原型：结论、反例和证据边界

日期：2026-10-16。现行产品决定以 [ADR-0008 / ELDER_REMINDER_V2](../adr/0008-photo-first-elder-reminders-and-caregiver-handoff.md) 为准；本报告保留历史观察，不构成第二套规范。2026-10-17时序修正覆盖当前规范：三十分钟只通知照护者，两小时退出，T−5/T+5两次失败才通知连接异常；原型本身不改，其三十分钟退出/两分钟失联模拟已过时。剩余技术实现仍需确认。整理自用户多轮反馈、现有代码和当前截图；没有真实长者参与的可用性试验，不虚构通过率或审批。

交付入口：[Issue #23](https://github.com/BRMRs/group33/issues/23)；执行方向：[UI 基线](../ELDER_UI_BASELINE.md)；现行产品决定：[ADR-0008](../adr/0008-photo-first-elder-reminders-and-caregiver-handoff.md)。

## 1. 这次原型回答了什么

| 设计问题 | 收敛答案 | 证据性质 |
| --- | --- | --- |
| 核心使用者是谁 | 能自己取药服药、不适合复杂手机管理的长者；照护者承担异常管理 | 用户明确确认，非人群研究 |
| 主页是否呈现今天所有药 | 不呈现，保持安静，拍药盒是独立日常入口 | 用户明确反馈 |
| 单药与多药是否应成为不同操作系统 | 否；都用照片识别和相同三个操作 | 用户选择与原型路径 |
| 同时多药是否逐盒完成 | 否；尊重先取齐再一起吃，只做整组确认 | 用户明确确认 |
| 部分服用/缺药如何交互 | 不让长者逐药/逐片登记；主动求助，照护者联系补登记 | 用户明确否定原有表单 |
| 延后是否需要照护者介入 | 否；固定十分钟是合理自主选择，但不能延长原始截止 | 用户纠正过度简化 |
| 照片如何排 | 六盒两列三行；稳定总览优于逐盒向导/移动选择 | 产品方向已选，不等于识别效果已证实 |
| 同步由谁关心 | 不占长者日常页面；照护者看收到什么、何时收到、哪些未知 | 用户明确确认；真实协议待审 |
| 无回应和连接异常是否同一种异常 | 否；三十分钟未确认通知照护者但长者保留至两小时，T−5/T+5两次无响应才连接告警 | 2026-10-17最新确认；原型旧时序不再作为规范 |
| 当前 C 是否可直接照着开发 | 不可以；按钮挤压照片、滚动遗漏风险仍未解决 | 截图和历史布局测量 |

## 2. 为什么不能再把“大按钮”当成主要答案

历史浏览器检查在 360×800、默认字体下记录：照片视窗约 329px，全部照片内容约 599px；每列约 144.5px 宽，单卡约 189px 高；主按钮约 72px、两个次按钮各约 64px，操作区含间距约 226px。这是原型 CSS 像素，不是 Android dp/sp；不能据此宣称跨设备合格。

照片/操作两区单独相比约 59:41，但这个比例忽略标题、工具栏和屏幕环境；真正重要的是仅一整排完整、第二排被截断、第三排不在首屏。由此不能订立一个机械的“60:40 适老比例”。本轮重新查看了存档截图，与用户指出的问题一致。

证据：[当前 C 六盒截图](https://github.com/BRMRs/group33/blob/60b035a72255cf0c3f11d15f900438ca0809637c/android-app/prototypes/due-reminder-prototype/preview-c-v2.jpg)，[当前 CSS](https://github.com/BRMRs/group33/blob/60b035a72255cf0c3f11d15f900438ca0809637c/android-app/prototypes/due-reminder-prototype/c-v2.css)。

“能滚到底且按钮不挡末项”只回答布局有没有遮挡；并没有回答老人会不会意识到下面还有药。照片是任务主体，操作区应该服务于它。操作目标不能缩到难点，但也没有理由每个操作都用巨大全宽卡片并挤掉药盒。

## 3. 滚动遗漏的具体风险

1. 首屏两盒看起来像完整清单，下方药盒在心理上不存在。
2. 老人放下手机找药后忘记阅读位置；滚动不是持续专注的屏幕任务。
3. 照片或用量在视窗边缘被截开，增加配对错误风险。
4. 统一“药吃好了”仍可被点击，系统无法由此知道是否每盒都看过。
5. 多层滚动、放大返回丢位置或字号切换重排，使同一个药盒难以再次定位。

这些是基于任务的风险分析，不是已观察到的发生率。不能说“有共六盒文字/滚动条就不会漏”，也不能用逐药必选、强制读完步骤来解决。默认六盒以完整可辨同屏为有限验收目标；若做不到，应暴露未通过项，由共用组件负责人统一决策，而不是各成员各自折中。

## 4. 迭代中应保留的教训

- A/B/C 曾比较大图、逐盒浏览、照片总览以及不同部分服用选择。它们是历史探索，不是三个可由成员自由挑选的生产方案。
- 用户偏好 C 的视觉总览，但否定其移动分组/逐药报告；选择 C 不代表接受它曾经的所有状态和交互。
- 解释文字不是免费帮助：“点击看大图”、重复返回说明、毫克信息和重复时间会争夺注意力。
- 删除所有次操作也不是简化：曾删除延后，误把正常忙碌归类为求助。
- 将异常交给照护者不是隐藏异常：必须有可收到、可跟进、需补登记、未确认不消失的真实闭环。
- “已联系”不是结果，“无法确认”不是失败按钮也不是可标绿的成功；时间不清楚应允许明确未知。
- 实际原药盒照片比抽象药名更符合此次方向，但示例照片包含一图多盒、混规格、背景杂乱等问题，不足以证明六盒都好认。
- 200% 是兼容性和无障碍验收，不是长者必用设置，也不能从用户觉得默认够大推断无需系统字体适配。
- 当前前端模拟实现了许多分支，不代表对应 Android/Server 能力已存在。不能让一个模拟页面反向偷偷修改 Accepted 领域含义。

## 5. 已做和没做的验证

原型既有检查记录于 [C v2 notes](https://github.com/BRMRs/group33/blob/60b035a72255cf0c3f11d15f900438ca0809637c/android-app/prototypes/due-reminder-prototype/C_V2_NOTES.md)，以下是历史检查，不是本轮重新做完全部流程：

- 历史已模拟（非当前时序验收）：主页/单药/多药、十分钟延后与原始截止、旧三十分钟退出/两分钟失联告警、离线/关机恢复不重放、照护者三种补登记、明确未知时间、延迟报告冲突保留、样例拍照预览/重拍/保存及收件。
- 已做浏览器布局检查：中英文、320px/360px、100%/200% 字体模拟、末项可滚到且不被动作区盖住。**无横向溢出不是照片识别或操作负担验收。**
- 未做：真实长者取六盒药的任务观察、照片识别准确性、按钮误触概率、手抖/低视力操作、真实手机拍照、Android TalkBack 与实际字体缩放、持久化/重启闹钟、真实后台网络、通知送达/已读及照护者响应时效。

本轮只审阅、归纳并留档，不修改原型或重测上述全部分支。研究参考来自 W3C/Apple Assistive Access/GrandPad/Doro 等已有记录，只帮助提出设计原则，不证明本产品适老性。原始来源与各药盒照片署名/许可保留在存档的 [C_RESEARCH.md](https://github.com/BRMRs/group33/blob/60b035a72255cf0c3f11d15f900438ca0809637c/android-app/prototypes/due-reminder-prototype/C_RESEARCH.md) 和 README；分组与用量仅是虚构交互数据。

## 6. 剩余工作必须有边界

不再扩展 Web 原型；不再比较三个新风格。只保留三项明确交付：

1. **技术迁移**：按 V2-T01–T05 完成协议/版本/数据/通知机制评审和代码/向量迁移，形成同版 Android/Server 签署。三十分钟通知/两小时退出、T−5/T+5两次失败告警、照护者补登记已是当前规则，不做全天监测；页面作者不得私定共享字段。
2. **共享布局收口**：#19 中 C1/E 在一套参考组件里一次性锁定布局/token/双语状态；记录目标设备六盒完整可辨、三操作热区/取消点击、系统放大兼容。缺陷不通过，不另开全面原型竞赛。
3. **必要真实任务观察**：让目标长者使用本人熟悉或经确认的测试药盒，找齐六盒、忙时延后、找不到时求助；观察漏看和误触，不让其真实改变服药。记录设备、字号、漏看/求助/误触及需协助情况。尚无经过同意的参与者、样本和合格阈值，不编造完成结论，由负责人在 #21 明确后执行。
