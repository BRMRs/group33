## Failure and correction

The previous adapter configured a lock wait limit only. A long-running SQL statement could keep the capability guard and a request occupied until it completed or the connection's socket deadline expired. Socket failure is not a database-confirmed cancellation and can leave a server query running. Slow deferred checks at final COMMIT also require explicit treatment.

The capability transaction sets transaction-local `statement_timeout` to five seconds alongside its existing `lock_timeout`, before acquiring the guard. After all business and original receipt writes, `SET CONSTRAINTS ALL IMMEDIATE` runs pending deferred checks under the statement budget in the same transaction, before final COMMIT. [PostgreSQL 17 statement/lock timeout behavior](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-STATEMENT-TIMEOUT) and [constraint check timing](https://www.postgresql.org/docs/17/sql-set-constraints.html) describe these distinct controls. SQLSTATE55P03 still maps to the existing retryable409/Retry-After1 contention result; other SQL failures retain the existing sanitized retryable503 HTTP response. No global configuration, schema, public field, status code or retry policy changes.

Database-confirmed cancellation before successful COMMIT rolls back observation, current projection and operation receipt together. An explicit same-input retry retains its original report ID. Delayed lower-sequence acknowledgement never replaces newer current state; accepted historical receipts still replay unchanged. This is a per-statement/check budget, **not a universal five-second request, final COMMIT or durability bound**. A lost COMMIT/HTTP acknowledgement may still mean the original operation committed; reconcile that original operation rather than allocating another report ID or deleting evidence. No automatic retry or cleanup is added.
