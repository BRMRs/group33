## 1. 负责人已确认，不再重复询问

- 没有旧版App用户；首发不增加旧客户端兼容层或既有用户数据迁移。当前r1开发声明、JSON和两端测试仍需协调更新到V2，不能只改版本字符串。
- 同一位长者、同次提醒的全部药品一次操作，整组全收或全拒；一侧事务不能部分业务接受。两端不是一个分布式事务，本机记录与Server接收之间允许有待同步状态。
- 当前跟进结论以照护者有权限、已被服务接受的有效登记为准；长者迟到报告不自动覆盖。双方原始报告、来源、实际时间或明确未知、登记和接收时间及更正历史保留；不伪造Elder Taken。无法确认仍待核实。
- T+30分钟未获知确认仅通知照护者，长者继续操作；T+2小时才截止`[T,T+7_200_000ms)`。整组十分钟延后不重置这两个时点，截止优先。Taken、Help或长者设备确认的接管可提前结束催促。
- 连接初查T−5分钟、复查T+5分钟；各自等待后都无本轮有效回复才通知，任一次有效回复可阻止本轮两次失败告警。没有全天心跳、实时失联监护或没电原因诊断。

## 2. 已授权做初版的时间参数

| 项目 | 初版规则 | 验证边界 |
|---|---|---|
| 单次探测等待 | 60秒；记录计划与实际发出时点，等待从实际尝试发出计 | 漏执行不能当设备无响应；具体调度、认证、迟到与超时并发由S1/S2共同验证 |
| 告警可见 | Server持久化告警到照护设备可见，目标15秒，首轮检查上限60秒 | 条件为正常联网且通知可用；不是离线送达承诺或厂商时限保证 |
| 无回执传输重试 | 首次后名义15/60秒，含首发最多3次，沿用同一告警ID | 后续间隔按实际发送计15/45秒，晚恢复不能突发补发；通道接受不等于设备回执 |
| 已收到但未处理 | 收到后名义2/5分钟各再提示一次 | 若第一次执行晚，第二次至少间隔3分钟；次数耗尽不能结掉未解决跟进，已读/已联系不等于已处理 |
| 迟到回复 | 最终告警判定前已保存的有效回复阻止本轮告警；告警已创建后到达则记录连接恢复 | 不自动改服药结果或关闭待核实；已发生的回复/告警不能因墙钟回拨失效 |

上述参数已由负责人授权实施初版；实际通道可行性、端到端时限和生产适配仍待验证。不能把它们继续标成“数值未选”，也不能标成已经实机达标。短信、额外联系人和全天监测没有新增授权。
