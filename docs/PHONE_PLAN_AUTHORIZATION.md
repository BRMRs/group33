# Bound phone authorization for plan changes

Refs #118 and #53. This document covers the locally verifiable PS2 plan authorization slices: edits and deactivation of existing reminder plans (#145), plus initial plan confirmation and authorized medication/plan collection reads. It uses the database adapter from #143 and the typed phone profile from #144.

The internal plan entry points validate the token before acquiring a database connection. For initial plan confirmation and plan mutations, the PostgreSQL adapter locks the current account, installation and session, then acquires the existing pairing guard in that order. Plan or ready-photo lookup, current Elder identity and active caregiver relationship checks, the existing confirmation or mutation effect, and the original receipt run through that single connection. For medication and reminder-plan collection reads, the PostgreSQL adapter opens a single read-only `REPEATABLE READ` snapshot transaction, checks the current non-revoked phone account, installation, session, non-ambiguous principal directory identity, and either self-Elder ownership or active Caregiver relationship without acquiring `pairing_issuance_guard` or writing receipts. Both paths refuse ambiguous IDs present in both identity stores. Existing anonymous plan routes continue to use their own actor path.

A new session on the original installation can recover the original confirmation or mutation receipt while the relationship is current. A different installation cannot take over the operation. Revoking the session or the relationship blocks replay and collection reads as well as new effects. The receipt remains tied to the original command and plan revision. The new implementation calls the existing plan confirmation and mutation algorithms, preserving frozen revisions and conflict behavior.

The PostgreSQL tests use a real store with fictional accounts, an existing plan and a consented relationship. They verify single-connection confirmation, edits, deactivation and read-only collection snapshots, replay across re-login, cross-installation rejection, session and relationship revocation, Elder self-read vs Caregiver relationship-scoped read, non-blocking read snapshots when `pairing_issuance_guard` is locked, ambiguous identity rejection, and signature failure before any database connection. The existing Server and Android regression suites are also run.

Pairing creation and consent, photo upload/content access, and event or reminder registration must adopt their relevant current-actor checks in subsequent PS2 slices. Real provider, signed APK and joint device cases remain separate.
